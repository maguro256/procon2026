# 卒研の相談用：システムとレジュメの全体像

高専の卒業研究（チーム開発）です。私は**タスク割当 AI（WariAthena）**の担当です。
以下は、発表レジュメ（A4 2段組 2ページ、LaTeX）と実装の内容をまとめたものです。
この内容をもとに、**既存の割当手法との比較実験の設計**と、**レジュメの書き方**を相談したいです。

---

## 1. 研究の概要

- **題目**：共有機材の現場における NFC タッチ起点のタスク自動割当システムと、実績から学習する割当 AI の開発
- **副題**：予約をなくし、タッチした瞬間に「今やるべき仕事」を渡す
- **背景**：工場の共有機材（レーザー加工機・旋盤・プレス機など）では、次の非効率が起きやすい。
  - 誰が何に使っているか分からない
  - 予約はあるのに来ない（ゴースト予約）
  - 重要な仕事が特定の人に偏る・忘れられる
  - 専任の IT 担当者がいない中小工場では、計画を立てるコストと、空いている機材や仕事を探すコストが負担になる（ものづくり白書・中小企業白書を引用）
- **狙い**：各機材に NFC リーダー付きのモジュールを置く。社員証をタッチした瞬間に、その人が今その場所でやるべきタスクを提示する。遠隔予約の機能はあえて持たず、物理的なタッチだけを操作の起点にする。これにより、システム上の状態と現場の実態が常に一致する（ゴースト予約が原理的に起きない）。
- **貢献（レジュメ記載）**
  1. システム：NFC タッチ起点の割当・排他制御・誘導
  2. 割当 AI：作業者ごとのベイズ線形回帰と Thompson Sampling による文脈付きバンディットとして定式化。手持ちの仕事量による負荷分散と、資格によるハード制約を組み込んだ。
  3. 評価：シミュレーションで、経験年数順などの割当と比較した。

## 2. システム構成

- **機材モジュール**（機材ごとに1台）
  - 試作機は Raspberry Pi 4 に、NFC リーダー（RC522）、2.8インチ LCD（ILI9341）、物理ボタン3個（左・決定・右）、状態 LED（作業中は赤、それ以外は青）をつないだもの。
  - 量産は ESP32 へ移す計画。
- **通信**：サーバとは MQTT で双方向に通信する。ブローカーは自動探索し、切断は Last Will で即時に死活表示へ反映する。
- **サーバ**：Flask + SQLite。
  - テーブルは、作業者（workers）、機材（equipment）、タスク（tasks）、作業ログ（work_logs）。
- **管理画面**（ブラウザ）：ダッシュボード、タスク管理、作業者管理、機材管理の4画面。
  - タスクの登録項目：重要度、難易度（1〜5）、数量、期限、必要な資格
  - AI による割当と、その根拠の表示
  - 稼働状況の表示
  - 画面からの機材予約は、ゴースト予約を防ぐため意図的に作っていない。
- **補助機能**：音声からのタスク登録（STT）、未登録タグ・未登録モジュールの紐付け、キーボードでタッチを模擬するシミュレータ。

### 現場の流れ

1. 空いている機材で社員証をタッチすると、候補タスクが1件ずつ LCD に出る。
2. ボタンで承認すると、機材がロックされる。他者のタッチは拒否される（排他制御）。候補が無い、またはすべて断ったときは「フリー利用」としてロックする。
3. 他の機材に本人宛のより重要なタスクがあれば、そちらへ移るかを尋ねる（誘導）。
4. 再タッチで完了する。所要時間を作業ログに記録して機材を解放し、直後に体感難易度（簡単・普通・難しい）を尋ねる。

## 3. 割当 AI（WariAthena）の中身

### 問題設定

作業者を「腕」、タスクの特徴を「文脈」とする文脈付きバンディットとして扱う。
実績のある人に任せる「活用」と、まだ分からない人に任せてみる「探索」を両立させる。

### 文脈ベクトル

タスク j を作業者 w に任せるときの文脈を、次のように定める。

```
x = [ y, d, y·d, e_diff, e_perm, e_eq ]
```

- `y`：勤続年数 / 30
- `d`：難易度（1〜5 を 0.15〜0.85 に写す）
- `e_diff`：難易度の one-hot（5次元）
- `e_perm`：必要な資格の multi-hot（溶接・クレーン・検査など）
- `e_eq`：機材の one-hot（実績のある機材だけ）

資格と機材を入れたのは、難易度だけでは「溶接が得意な人」「旋盤が得意な人」を区別できないため。

### 報酬

```
r = c_f × (同じ難易度の過去の1個あたり平均時間) / (今回の1個あたり時間)
c_f ∈ {1.5, 1.0, 0.5}
```

- 所要時間は数量で割って、1個あたりにそろえる（割らないと、大量のタスクを引いた人が「遅い」と学習されるため）。
- `c_f` は本人の体感難易度（簡単・普通・難しい）の係数。
- 未回答のときは、今回の時間が平均より1割以上速いか遅いかで決める。

### 学習

- 作業者ごとに `r ≈ θ_wᵀ x` の線形モデルを置く。
- 事前分布は `N(0, 100I)`、観測雑音は `σ² = 0.1`。ベイズ線形回帰で事後分布 `N(μ_w, Σ_w)` を更新する。
- 更新は足し算なので、学習結果は保存しない。作業ログを古い順に再生して毎回組み立て直す（再起動しても失われない）。

### 選択（Thompson Sampling）

- 各作業者の事後分布から θ を1本ずつ引き、予測報酬 `r̃_w = θ̃_wᵀ x` で比べる。
- 実績の少ない人は分布が広く、ときどき大きな値を引くので、自然に試される。

### 負荷分散

予測報酬だけで選ぶと、何でも速いベテランに仕事が集まる。そこで次の点数で選ぶ。

```
s_w = r̃_w / (1 + L_w / T̂_j)     （r̃_w < 0 のときは掛ける）
```

- `L_w`：作業者 w の手持ちの残り時間
- `T̂_j`：このタスクの見積もり時間（難易度ごとの平均 × 数量）

引き算ではなく割り算にしたのは、`c_f` があるため報酬が速さに比例せず、尺度が一定でないから。
割り算なら尺度に依らず、得意・不得意の差が大きい仕事ほど任され続ける。

### 資格はハード制約

資格（フォークリフト・クレーン・溶接など）は学習させず、AI を呼ぶ前に候補から除く。
無資格者に危険作業を任せて失敗から学ぶ設計は成り立たないため。

### 使い方は2通り

- **(a) 現場でタッチされたとき**：その人の θ を1本だけ引き、候補タスクを予測報酬の順に並べる（作業者 → タスク）。
- **(b) 管理画面の「AI 割当」**：タスクに対し、`s_w` が最大の人を選ぶ（タスク → 作業者）。各候補の期待値・引いた値・手持ち・除外理由を、根拠として画面に残す。

## 4. 現在の評価（シミュレーション）

### 設定

- 作業者は6名（勤続 1, 3, 8, 15, 25, 30 年）。真の時間倍率は AI に隠して与える。
  - ベテランほど全体に速い（倍率 `1.3 − 0.5y`）。
  - 個人差として ±30% をつける。
  - 各人に1つ、得意な作業（溶接・検査・プレスのいずれか）があり、その作業は倍率 ×0.6。
- タスクは、難易度 1〜5（標準 1〜10 分/個）、数量 1〜5、種類4通りを一様に生成する。
- 1ラウンドで6件を順に割り当てる。ラウンドの終わりに全員が作業を終え、ログに加わる。
- 150ラウンド、20試行の平均をとる。割当 AI は実装をそのまま呼ぶ。

### 指標

- **適性比**：任せた人の時間倍率 / そのタスクに最適な人の倍率（1 が最良）
- **完了時間**：1ラウンドで最も遅い人が終わるまでの時間
- **偏り**：最も多く担当した人の割合

適性比と完了時間は、学習後（51ラウンド目以降）で測る。

### 結果

| 方式 | 適性比 | 完了時間 [分] | 偏り |
|---|---|---|---|
| ランダム | 1.73 | 44.4 | 19% |
| 順番（ラウンドロビン） | 1.72 | 34.7 | 17% |
| 経験年数が最長の人 | 1.27 | 63.7 | 100% |
| 提案（負荷分散なし） | **1.03** | 32.4 | 42% |
| **提案** | 1.16 | **25.4** | 27% |
| 参考：真の適性を知る貪欲法 | 1.21 | 23.6 | 24% |

- 負荷分散なしの提案は、作業ログだけから隠れた得意分野を見つけ、ほぼ最適な人を選べる。ただし、得意な人に仕事が集まる。
- 負荷分散ありの提案は、完了時間が経験年数による割当より 60%、順番より 27% 短い。真の適性を知る貪欲法との差は 8%。
- 「各人に一番向く仕事」と「全体が早く終わる割当」は一致せず、後者には負荷分散が要る。

### レジュメに書いた限界

- 評価はシミュレーションのみで、実際の工場の作業ログはまだ無い。
- 作業者の適性は時間とともに変わらないと仮定した（実際は熟練で速くなる）。
- ログから毎回学習し直すので、ログが増えると計算が重くなる。
- 「指定した人に任せる」タスクは未対応。

## 5. 新規性についての自己分析（Claude Code との議論）

### アルゴリズム単体の新規性は薄い

提案の各要素には、次のような既存手法・分野がある（文献は要確認）。

- ベイズ線形回帰＋TS：LinTS（Agrawal & Goyal, ICML 2013）、LinUCB（Li et al., WWW 2010）
- 能力が未知の作業者への学習しながらの割当：クラウドソーシングのオンライン割当（Ho & Vaughan, AAAI 2012／Ho, Jabbari & Vaughan, ICML 2013／Tran-Thanh et al., AIJ 2014）
- 処理速度が未知のサーバへの割当：Queueing bandits（Krishnasamy et al., NeurIPS 2016）
- 負荷を見て最も早く終わる人に振る：異種マシンのスケジューリング（R‖Cmax）、MCT 法（Braun et al., 2001）。表の「真の適性を知る貪欲法」は MCT そのもの。
- スキルに応じた振り分け：コールセンターの skill-based routing（Gans, Koole & Mandelbaum, 2003）
- 資格による除外：制約付き割当。安全性の観点では conservative bandits（Kazerouni et al., 2017）が近い。

### 主張できそうな点

1. **pull 型・場所制約付きの割当**：作業者が特定の機材の前にいる瞬間に決める。同じ事後分布を「作業者 → タスクの並べ替え」と「タスク → 作業者の選択」の2方向で使う。別の機材への誘導もある。
2. **予約をなくしたことでログの質が上がる**：タッチで開始と終了を取るので、実測時間が正確になり、報酬の信頼性を支える。
3. **報酬の設計**：数量での正規化、難易度ごとの平均との比、本人の体感申告を組み合わせた（係数の根拠は弱い）。
4. **実験の知見**：「各人に一番向く仕事」と「全体が早く終わる割当」は一致しない。
5. **根拠の表示**：判断の理由を現場向けに見せる。

### 実装上の弱点

- モデルは作業者ごとに独立しているので、同じ作業者の中では勤続年数 y が一定。そのため `y`、`d`、`y·d` は難易度 one-hot の線形結合になり、情報を足していない。
- 事前分布も作業者ごとに独立なので、新人の予測に勤続年数が使われていない（コールドスタートに年数が効いていない）。
- 改善案：全員で共有する部分と個人差の部分に分けるモデル（hybrid LinUCB 的な構造、または階層ベイズ）。
- 比較対象が学習しない手法だけなので、「学習するなら何でも勝つのでは」と言われる。
- 負荷分散の割り算 `s = r/(1+L/T)` は経験則で、理論的な根拠がない。

## 6. やりたいこと：既存手法との比較実験

**目的**：「○○との比較で〜なことがわかった」と言える結果を出したい。

### 比較したい手法（学習器）

- 平均時間表（作業者×種類ごとの平均時間。探索なし）
- **Elo レーティング**（作業者とタスクの対戦とみなす。1個あたりの時間が難易度ごとの平均より速ければ作業者の勝ち）
  - 1次元の Elo（1人1つのレート）
  - 種類別 Elo（溶接用、検査用…と種類ごとにレートを持つ）
- ε-greedy
- LinUCB
- LinTS（提案）

### 選び方（学習器と組み合わせる）

- 貪欲：推定が一番良い人を選ぶ
- 割り算の負荷分散（提案）
- MCT：手持ち＋予測時間が最小の人を選ぶ

### シナリオ

- 静的（今の設定）
- 新人加入（途中で1人追加し、立ち上がりの速さを比べる）
- 熟練による変化（時間とともに速くなる作業者を入れる）

### 期待している「わかったこと」（仮説）

1. 1次元の Elo と、種類別 Elo／LinTS の比較：個人の得意分野を捉えるには、多次元のモデルが必要。
2. 種類別 Elo と LinTS の比較：探索と不確かさを持つと、得意分野を早く見つけられる。差が出なければ「現場規模なら単純な Elo で十分」という結論になる。
3. 負荷分散をすべての学習器に付けた比較：完了時間を縮めているのは主に負荷分散で、学習器の差は適性比に表れる。
4. 熟練による変化のシナリオ：Elo は古い結果を忘れるので、提案より強い可能性がある。そうなれば、今後の展望（古いログの割引）に根拠を与えられる。

### 注意すること

- Elo の K、ε、LinUCB の α は数個の値で試し、一番良かった値で公平に比べる。
- 平均値に加えて、標準偏差（エラーバー）を示す。
- レジュメは2ページなので、表1つとグラフ1つに収まる規模にする。
